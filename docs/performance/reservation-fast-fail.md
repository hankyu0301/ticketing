# 좌석 경합을 분석하고 빠른 실패로 예약 지연 줄이기

같은 좌석에 300명이 요청하면 예약은 한 건만 성공한다. 문제는 나머지 요청도 락을 얻고 DB에서 좌석 상태를 확인한 뒤 실패하면서 오래 기다린다는 점이었다.

## 지연은 어디서 발생했나

단일 좌석에 300명이 요청하는 실험에서 성공 1건·경쟁 실패 299건이 기록됐다. 내부 계측을 붙인 진단 실행에서는 다음 결과가 나왔다.

| 실패 요청의 관측 지표 | 값 |
| --- | ---: |
| 락 Executor 전체 p95 | 3,892.05ms |
| 예약 서비스 p95 | 10.94ms |
| Hikari 커넥션 대기 | 0 |

서비스의 실패 판단은 짧았지만 락 획득부터 서비스 호출·해제까지의 경로에서 지연이 컸다. 이 결과를 바탕으로 이미 선점된 좌석의 요청이 락 경로에 오래 머무는 비용을 줄이기로 했다.

## 캐시로 먼저 거르고, 남은 요청의 락 대기를 제한했다

- **예약 불가 캐시**: 이미 선점된 좌석이면 락과 DB 처리 전에 `400`으로 응답한다. 반복 요청이 같은 락을 거치는 비용을 줄인다.
- **짧은 락 대기**: 캐시가 채워지기 전에 들어온 요청도 오래 기다리지 않도록 한다. 제한 시간 안에 락을 얻지 못하면 `429`로 응답한다.

```text
기존: 락 획득 → DB 상태 확인 → 이미 선점됐다면 실패
개선: 캐시 확인 → 예약 불가면 즉시 실패
               → 캐시가 없으면 제한 시간 안에 락 획득 → DB 상태 확인
```

[예약 Facade](../../src/main/java/com/ticketing/application/reservation/facade/DistributedLockReservationFacade.java)는 선점 성공 후 DB 커밋과 락 해제를 마친 뒤 캐시를 기록한다. 결제·만료에 따른 캐시 변경도 커밋 후 이벤트로 처리한다. 캐시가 없는 요청은 락 안에서 DB 상태를 다시 확인한다.

## 예약 p95가 2,053.08ms에서 637.11ms로 줄었다

로컬 Docker의 `loadtest` 프로필에서 같은 좌석에 300명이 한 번씩 요청했다. active 사용자는 500명을 미리 등록하고 캐시와 락 대기 시간을 비교했다.

| 조건 | 예약 p95 | 성공 201 | 경쟁 실패 400 | 락 대기 초과 429 |
| --- | ---: | ---: | ---: | ---: |
| 캐시 OFF·대기 10초 | 2,053.08ms | 1 | 299 | 0 |
| 캐시 OFF·대기 300ms | 1,022.68ms | 1 | 25 | 274 |
| 캐시 ON·대기 300ms | 637.11ms | 1 | 277 | 22 |

대기만 줄였을 때는 `429`가 274건 발생했다. 캐시를 함께 사용한 실행에서는 22건으로 줄었고, 기존 조건 대비 예약 p95는 **약 69.0% 감소**했다. 세 조건 모두 예상 밖 실패와 dropped는 0건이었다.

이미 선점된 좌석에 다시 요청한 비교에서도 캐시 적용 시 `429`가 **232건 → 0건**, p95가 **550.19ms → 445.44ms**로 줄었다.

## 최종 락 대기는 200ms로 정했다

캐시를 켠 상태에서 같은 단일 좌석·300명 조건으로 대기 시간을 추가 비교했다.

| 락 획득 대기 | 예약 p95 | 락 대기 초과 429 |
| --- | ---: | ---: |
| 100ms | 1,170.51ms | 294 |
| 200ms | 537.73ms | 65 |
| 300ms | 735.75ms | 58 |
| 500ms | 951.83ms | 77 |

이 비교에서는 200ms의 p95가 가장 낮았다. 300ms는 `429`가 7건 적었지만 p95가 약 36.8% 높아, 현재 설정은 **200ms**로 두었다. 이 값은 [Executor](../../src/main/java/com/ticketing/infrastructure/lock/executor/RedissonLockExecutor.java)의 락 획득 대기 시간이다.

## 500석 경합에서도 중복 예약 없이 처리했다

인기 좌석 500석에 초당 150회씩 2분간 **18,000건**을 요청했다. 예약 성공은 **500건**, 나머지 **17,500건은 경쟁 실패 `400`**으로 처리됐으며 중복 예약·`429`·예상 밖 실패·dropped는 모두 0건이었다.

실행 방법은 [부하테스트 가이드](../../loadtest/README.md)를 참고한다. 성능 수치는 DB 조건부 갱신을 추가하기 전의 로컬 측정값이다.
