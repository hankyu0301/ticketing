# 예약 부하테스트로 Tomcat·Hikari 병목 분석하기

예약 API가 느리면 먼저 SQL부터 의심하기 쉽다. 하지만 DB에 도착하기 전부터 요청이 밀리고 있다면, 쿼리만 고쳐서는 지연을 해결하기 어렵다.

같은 좌석을 놓고 경쟁하는 상황을 분석하기 전에, 서로 다른 좌석을 예약할 때의 처리량부터 확인했다. 좌석 경합을 제외해도 요청이 밀린다면 예약 경로 자체에서 먼저 확인할 문제가 있기 때문이다.

## 서로 다른 좌석을 예약하도록 만든 이유

같은 좌석에 요청이 몰리면 성공할 수 있는 예약은 제한된다. 실패 응답이 많아진 원인이 좌석 경합인지, 서버의 처리 여력 부족인지 구분하기도 어려워진다.

그래서 첫 테스트는 요청마다 다른 좌석을 선택하도록 구성했다. 성공 가능한 요청을 계속 보내면서, 예약 경로가 목표 요청량을 처리하는지 확인하려는 목적이다.

## 무엇을 포함해서 측정했는가

| 항목 | 실험 조건 |
| --- | --- |
| 실행 환경 | 로컬 PC의 Docker Compose, `loadtest` 프로필, MariaDB 10.6·Redis 7 |
| 요청 목표 | 60초 동안 30,000회, 초당 500회 |
| 사용자 세션 | 최대 1,000개 |
| 좌석 | 같은 회차의 서로 다른 좌석 50,000석 |
| 기존 데이터 | 회원 10만 명, 예약 이력 30만 건, 결제 이력 24만 건 |
| 포함한 처리 | 세션·CSRF, active 검증, Redisson 락, 좌석 변경, 예약 저장 |
| 제외한 처리 | 대기열 진입·순번 대기, BCrypt 로그인, 결제·RabbitMQ 처리량 |

대기열 진입부터 측정하면 입장 정책과 예약 처리 비용이 섞인다. 이번에는 Redis active set에 사용자를 미리 넣어, 이미 입장한 사용자가 예약하는 상황을 만들었다. 예약 API의 active 검증과 만료 시각 연장은 그대로 수행한다.

로그인도 전용 세션 API로 미리 준비했다. 비밀번호 해시 검증 비용은 제외하지만, 실제 예약 요청의 세션과 CSRF 처리는 유지한다. 최대 1,000개 세션은 사용할 사용자 풀의 크기이며, 초당 1,000건이나 항상 1,000개 요청이 동시에 실행된다는 뜻은 아니다.

DB는 기준 볼륨을 실행용 볼륨으로 복사해 초기 상태를 맞췄다. 앞선 실행이 좌석을 선점한 상태라면 다음 실행의 성공률과 처리 비용이 달라지기 때문이다.

## HTTP 실패가 없는데 목표 요청량은 채우지 못했다

초기 실행의 HTTP 실패율은 0이었다. 이것만 보면 문제가 없어 보이지만, 완료한 반복은 25,563회였고 `dropped_iterations`는 4,438회였다.

`constant-arrival-rate`는 응답이 늦어져도 정해진 속도로 새 반복을 시작하려 한다. 기존 VU들이 요청을 처리하느라 반환되지 않고 추가 VU 한도에도 도달하면, 예정된 반복을 시작하지 못한다. 이 횟수가 `dropped_iterations`에 기록된다. 서버가 요청을 받고 거절한 횟수와는 다르다.

따라서 HTTP 성공률과 함께 **보내려던 부하를 실제로 만들었는지**도 봐야 한다. 이번에는 서버 지표에서 다음 신호가 함께 나타났다.

| 지표 | 초기 관측 | 의미 |
| --- | ---: | --- |
| Tomcat busy threads | 200 / 200 | 요청 처리 스레드가 상한까지 사용됨 |
| Hikari pending | 최대 50 | DB 커넥션을 기다리는 작업 발생 |
| Hikari idle | 0 | 즉시 빌릴 수 있는 커넥션이 없음 |
| DB row lock wait | 0 | 관측 구간에서 행 락 대기가 나타나지 않음 |

Tomcat 스레드는 예약 처리 중 Redis나 DB 응답을 기다리는 동안에도 점유될 수 있다. Hikari 커넥션 대기까지 길어지면, DB 쿼리를 실행하기 전부터 요청 처리 시간이 늘어난다. 이 관측을 바탕으로 스레드와 커넥션 대기를 먼저 완화하기로 했다.

## 기술적 대안

| 접근 | 기대하는 효과 | 선택할 때 확인할 점 |
| --- | --- | --- |
| SQL·인덱스부터 튜닝 | DB 실행 시간이 길 때 쿼리 비용 감소 | 느린 SQL과 실행계획이 원인이라는 근거가 필요하다. |
| Tomcat 스레드만 확대 | 더 많은 요청을 동시에 처리 | DB 커넥션 대기가 그대로면 대기하는 스레드만 늘 수 있다. |
| Tomcat·Hikari를 함께 조정 | 관측된 스레드 포화와 커넥션 대기를 완화 | DB의 연결 여력과 변경 후 지연을 함께 확인해야 한다. |

### Tomcat과 Hikari를 함께 조정한 이유

초기 실행에서는 Tomcat이 `200 / 200`까지 사용되고, Hikari에서도 최대 50개의 대기가 관측됐다. 한쪽만 늘리면 다른 쪽의 대기는 남을 수 있으므로 두 자원을 함께 조정했다.

스레드와 커넥션을 많이 만드는 것 자체가 목적은 아니다. 실제로 대기가 발생한 지점의 상한을 조정하고, 같은 부하에서 대기와 응답 시간이 줄어드는지 확인하는 선택이다.

## 설정을 바꾼 뒤 무엇이 달라졌는가

[application-loadtest.yml](../../src/main/resources/application-loadtest.yml)에 반영된 주요 설정은 다음과 같다.

```yaml
server:
  tomcat:
    threads:
      max: 400
      min-spare: 50
    accept-count: 200

spring:
  datasource:
    hikari:
      maximum-pool-size: 60
      minimum-idle: 20
```

Tomcat의 최대 요청 처리 스레드를 400개로 늘렸다. Hikari는 최대 60개의 커넥션을 사용할 수 있게 하고, 유휴 커넥션의 유지 목표를 20개로 설정했다. Hikari의 최대 크기는 사용자 수가 아니라 전체 DB 커넥션 수의 상한이다. 빌릴 수 있는 커넥션이 없으면 대기가 발생한다. [HikariCP 공식 문서](https://github.com/brettwooldridge/HikariCP#configuration-knobs-baby)

`accept-count`는 별도 의미를 가진다. Tomcat의 최대 연결 수에 도달했을 때 OS가 대기시킬 연결의 backlog 설정이며, 스레드 400개가 바쁘면 HTTP 요청 200개를 더 처리한다는 뜻은 아니다. [Tomcat 공식 문서](https://tomcat.apache.org/tomcat-10.1-doc/config/http.html)

설정 조정 전후의 비교 기록은 다음과 같다.

| 지표 | 조정 전 | 조정 후 |
| --- | ---: | ---: |
| 완료 iterations | 25,563 | 29,439 |
| dropped iterations | 4,438 | 561 |
| 예약 API 평균 | 861.22ms | 189.98ms |
| 예약 API p95 | 3,907.23ms | 1,271.36ms |
| Hikari pending 최대 | 50 | 0 |
| Tomcat busy 최대 | 200 / 200 | 314 / 400 |
| HTTP 실패율 | 0 | 0 |

예약 API p95는 약 67.5% 줄었고, Hikari 대기는 이 실행에서 0까지 내려갔다. 다만 `dropped_iterations`가 561회 남았으므로, 이 단계에서 목표 부하를 모두 처리했다고 할 수는 없다.

## 이후 별도 계측 실행에서는 30,000건을 처리했다

설정 비교 이후에는 내부 Timer를 추가하고 상태를 다시 초기화해 별도 실행했다.

| 지표 | 별도 계측 실행 |
| --- | ---: |
| 예약 요청 수 | 30,000 |
| dropped iterations | 0 |
| HTTP 실패율 / 예약 성공률 | 0% / 100% |
| 예약 API p95 | 86.05ms |
| DB에 반영된 예약 | 30,000건 |
| `TEMPORARY` / `AVAILABLE` 좌석 | 30,000석 / 20,000석 |
| Hikari active 최대 | 38 / 60 |
| Hikari pending 최대 | 3 |
| Tomcat busy 최대 | 177 / 400 |

요청 결과뿐 아니라 DB 반영 건수와 좌석 상태도 확인했다.

설정 변경 효과는 앞선 비교의 p95 `3,907.23ms → 1,271.36ms`를 기준으로 정리했다. 이번 `86.05ms`는 상태 초기화와 내부 계측을 거친 별도 실행 결과로 기록한다. 예약 지연 지표는 k6의 요청 전송·응답 대기·수신 시간 기준이다. [k6 지표 정의](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)

## 정리

초기 병목은 Tomcat 스레드 포화와 Hikari 커넥션 대기에서 나타났다. 두 설정을 함께 조정한 비교에서 예약 API p95가 약 67.5% 감소했고, 이후 별도 계측 실행에서는 초당 500회·60초의 예약 요청 30,000건을 dropped 없이 처리하고 DB 반영까지 확인했다.

이 기준선을 바탕으로, 다음에는 [같은 좌석에 요청이 몰릴 때의 락 경합과 빠른 실패 효과](./reservation-fast-fail.md)를 분석했다.
